# Audio analysis provenance — every result has a traceable origin

## Activate when

Use when designing, producing, reviewing, caching or exporting an audio *measurement* or visualization that needs its input sample region, clock/epoch, channel identity, algorithm choices, uncertainty or limitations traced. Not a generic literature-citation system, a waveform archive, a trusted timestamp/signature service, or a replacement for instrument calibration.

Read [the technical provenance contract](references/PROVENANCE_CONTRACT.md). Load [audio-timebase-sync](../audio-timebase-sync/SKILL.md) for sample and clock semantics, [audio-sample-formats](../audio-sample-formats/SKILL.md) for source representation, [audio-stream-buffering](../audio-stream-buffering/SKILL.md) for gaps and synthetic silence, and [audio-dsp-test-fixtures](../audio-dsp-test-fixtures/SKILL.md) for independent fixtures. Use [math-verification](../math-verification/SKILL.md) selectively to plan adversarial oracles; don't clone its general theory here.

## Engineering procedure

1. **Identify the measurement tap and actual evidence.** State whether data are captured, decoded, filtered, resampled, analyzed or merely displayed. Record source entity identity as *declared*, and record a SHA-256 digest only with an exact byte scope. An identifier, path, filename, or digest string is not verification that those bytes were supplied. Never synthesize a capture timestamp, channel order, missing input or instrument calibration.
2. **Preserve sample semantics.** Express each audio entity's exact rational sample rate (reduced numerator/denominator in Hz), independent clock-domain name, never-reused epoch, labelled channel order, sample format, and half-open integer sample interval `[start,end)`. Represent large sample indices as canonical decimal **strings**, not rounded binary64 JSON numbers. A rate conversion creates a new output sample-rate domain and epoch: 44.1→48 kHz uses `160/147` output/input, but two clocks are not shown to be synchronized just because nominal rates match.
3. **Explicitly account for missing/synthetic input.** Partition the audio entity span into contiguous labelled intervals: `observed`, `derived`, `gap`, `truncated`, `synthetic_silence`, or `unknown`. Do not conflate a gap with measured zero. Propagate missing, truncated, unknown-origin and synthetic flags through every derived artifact. A downstream rendering operation cannot convert an upstream gap into “clean observed audio.”
4. **Describe each operation, not merely the last output.** Use a small versioned directed acyclic graph: audio/analysis/visualization **entities**, `uses`/`generates` **activities**, and optional accountable software **agents**, inspired by W3C PROV-DM. Every processing activity identifies exact input/output IDs, algorithm/version and configuration; analysis results additionally identify source audio intervals, measured quantity, units/normalization and quantified or unquantified uncertainty. Rendering stores axes and display transform separately from measurement normalization.
5. **Validate contradictions instead of repairing them.** Reject duplicate IDs, missing references, cycles, multiple generators, impossible half-open segments, non-reduced rates, wrong rate ratios/output frame counts, unlabeled channel changes, invalid uncertainty bounds, nonfinite/untyped parameters and lost quality flags. Unknown origin may be represented honestly with explicit `unknown_origin`; do not invent a verified source to make a graph pass.
6. **Serialize and inspect with calibrated language.** [The standard-library bounded oracle](scripts/reference_provenance.py) validates a strict custom JSON subset, serializes sorted UTF-8 object keys without spacing, and computes SHA-256 over *record bytes*. It is **NOT** RFC 8785/JCS canonicalization, W3C PROV-O RDF, or a security attestation. Array order, strings and Unicode codepoints are retained; integers (other than schema structure) are decimal strings. Use `verify_entity_bytes()` with actual supplied bytes to compare a declared content digest; `matches_claim` means **only that those bytes match that claim**.
7. **Test failure before trust.** Run the [24 focused tests](../../tests/test_audio_analysis_provenance_reference.py) and inspect [independent trace expectations](../../tests/fixtures/AUDIO_ANALYSIS_PROVENANCE_TRACES.md): PCM→resampler→PSD→waterfall, exact 44.1→48 rate conversion, gaps/truncation/injected silence, channel-order changes, unknown source, duplicate/broken/cyclic graphs, reordered JSON map keys, modified parameters and digest mismatch, and privacy-sensitive metadata. Keep expected results independent from the implementation being tested.
8. **Evaluate reproduction separately.** A complete, internally consistent graph is still a *declaration*. To reproduce a measurement you also need the original bytes in the stated scope, correctly identified software/environment, executed parameters, available reference/calibration data and an independent output comparison. The oracle intentionally reports `reproducible: not_demonstrated` even for a matching content hash; do not promote it to success without executing the actual pipeline.

## Acceptance and limits

Before publishing an analysis result, preserve: input/epoch/range/channel/format, operation order and versions, output units/normalization, quality gaps and assumptions, identity claim versus byte check, and uncertainty state. Review linked entities by IDs, with privacy-minimized fixtures. The reference limits graphs to 32 entities, 32 activities, 16 agents, ≤65,536 frames/audio entity, ≤128 coverage segments, ≤128 KiB serialized JSON; it is offline, not a production content-addressed store, trusted log, parser for every WAVE format or real-time monitor. A best-effort privacy filter rejects common paths/email/token fields, **not** all possible personal data. The engineering team must review actual metadata for sensitivity.

From repository root run `python3 -m unittest -v tests/test_audio_analysis_provenance_reference.py`, `python3 tools/validate_seed.py`, `python3 -m unittest discover -s tests -v` and `git diff --check` where available. Record exact environment and results; passing structural tests does not establish PROV/RFC conformance, physical origin, measurement correctness, software identity or agent-use efficacy.

## Authoritative context

- [W3C PROV-DM, Recommendation 30 April 2013](https://www.w3.org/TR/prov-dm/) — entities, activities, derivations and optional responsible agents; source of modelling concepts, **not** a compliance claim.
- [W3C PROV-O, Recommendation 30 April 2013](https://www.w3.org/TR/prov-o/) — PROV-DM OWL2/RDF ontology; this skill's JSON graph is **not** a PROV-O serialization.
- [RFC 8785, June 2020](https://www.rfc-editor.org/rfc/rfc8785.html) — JCS and ECMAScript/I-JSON constraints; a useful comparison for why `json.dumps(sort_keys=True)` is **not** full JCS.
- [Python `hashlib`](https://docs.python.org/3/library/hashlib.html) and [`json`](https://docs.python.org/3/library/json.html) — actual reference hashing and serialization behavior.
